#######################
Disaster recovery guide
#######################

This guide explains how to replicate the persistent data of a deployment
towards a second region in order to survive the complete loss of the primary
region. It builds on top of the platform backups, which protect against the
loss of data, by adding continuous replication which protects against the
loss of a whole site with a much lower recovery point objective.

The replication is based on the snapshot-based RBD mirroring of Ceph, where
the ``rbd-mirror`` daemon of the secondary cluster pulls the periodic
snapshots of the mirrored pools from the primary cluster. The interval
between two snapshots drives the recovery point objective for the data
stored in the pool.

**********
Enablement
**********

Mirroring is configured between two independent deployments, each running
their own Ceph cluster. On both sides, you can enable the feature by setting
the following variables inside your inventory, listing the pools that must
be replicated:

.. code-block:: yaml

  atmosphere_rbd_mirror_enabled: true
  ceph_rbd_mirror_site_name: primary
  ceph_rbd_mirror_pools:
    - name: volumes-dr
      interval: 15m

Once the ``site.yml`` playbook (or the ``dr.yml`` playbook alone) has run on
the primary region, you need to generate a peer bootstrap token for every
mirrored pool by setting the following variable on the primary region:

.. code-block:: yaml

  ceph_rbd_mirror_bootstrap_create: true

The tokens are stored on the first controller of the primary region as
``/etc/ceph/rbd-mirror-peer-<pool>.token``. You can then copy the contents
of each token to the inventory of the secondary region, which imports them
and starts pulling the mirror snapshots:

.. code-block:: yaml

  atmosphere_rbd_mirror_enabled: true
  ceph_rbd_mirror_site_name: secondary
  ceph_rbd_mirror_pools:
    - name: volumes-dr
      interval: 15m
  ceph_rbd_mirror_peers:
    - pool: volumes-dr
      token: <contents of the token generated by the primary region>
      direction: rx-tx

The ``rx-tx`` direction allows the mirroring to be reversed after a
failover, which keeps the failback to the primary region possible. You can
use ``rx-only`` if the secondary region must never become a source.

**********
Monitoring
**********

The role installs a health check script on the controllers which prints the
state of every mirrored pool and exits with a non-zero exit code if any pool
is not healthy:

.. code-block:: console

  rbd-mirror-health volumes-dr

You can also inspect the mirroring state of a pool directly with the Ceph
tooling, which reports the daemon health, the image health and the number
of images per state:

.. code-block:: console

  cephadm shell -- rbd mirror pool status volumes-dr --verbose

********
Failover
********

The orchestrated failover and failback procedures, which promote the images
of the secondary region and reverse the direction of the mirroring, are
intentionally not automated by this role since they require an explicit
human decision. They are covered by their own runbooks.
